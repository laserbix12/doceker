## Changes Made

### 1. Made the Jenkins image available to Minikube
- **File:** `Jenkinsfile`
- **Change:** After building `api_test:${BUILD_NUMBER}`, the pipeline now loads that exact tag into Minikube with `minikube image load`.
- **Why:** Kubernetes was requesting `api_test:latest`, while Jenkins only built a numbered tag. Existing pods were stuck in `ImagePullBackOff`.
- **Revert:** Restore the original single-line Docker build command and remove the Minikube image-load block.

### 2. Deployed and waited for the PostgreSQL dependency
- **File:** `Jenkinsfile`
- **Change:** The deployment stage now applies `k8s/postgres.yaml` and waits for `deployment/postgres` to complete its rollout.
- **Why:** A fresh Kubernetes cluster did not receive the database deployment, so the Django container could not rely on PostgreSQL being available.
- **Revert:** Remove the `kubectl apply -f k8s/postgres.yaml` and PostgreSQL rollout-status commands.

### 3. Applied the build image tag and verified Django rollout
- **File:** `Jenkinsfile`
- **Change:** The pipeline now runs `kubectl set image deployment/django-backend django-backend=api_test:${BUILD_NUMBER}` and waits for the backend rollout.
- **Why:** `kubectl apply` alone reported success even while the application pods were unhealthy.
- **Revert:** Remove the `kubectl set image` and backend `kubectl rollout status` commands.

### 4. Fixed Kubernetes health probes
- **File:** `k8s/backend-deployment.yaml`
- **Change:** Readiness and liveness probes now send `Host: localhost`.
- **Why:** Django returned HTTP 400 because Kubernetes probes used the pod IP, which was not included in `ALLOWED_HOSTS`. The new pod therefore never became ready and was repeatedly restarted.
- **Revert:** Remove the `httpHeaders` blocks from both probes.
